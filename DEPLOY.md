# Deploying Fixtrail (test build)

One server runs both the API and the web app, so residents and service workers
use a single address. The login cookie works without any cross-site setup.

## 1. Create the cloud database (MongoDB Atlas)

Atlas is MongoDB's own cloud service and has a free tier (M0). It connects with a
`mongodb+srv://` connection string, which the server already supports.

1. Create a free account and a free **M0** cluster at https://www.mongodb.com/cloud/atlas
2. Create a database user: **Database Access** → add user with a strong generated password.
3. Allow connections: **Network Access** → add `0.0.0.0/0`.
   This is needed because free hosting platforms change IP addresses. It is acceptable
   for a test build, provided the database password is strong. Tighten it before real
   residents use the app.
4. Get the connection string: **Connect** → **Drivers** → copy the `mongodb+srv://…` string.
   Replace `<password>` with your password and add the database name `fixtrail` before the `?`.

## 2. Push the code to Git

Push this repository to GitHub or GitLab. Keep `.env` out of it; `.gitignore` already does this.

## 3. Deploy on Render

The repository includes `render.yaml`, which sets up the service for you.

### Option A (recommended): Blueprint

1. Render → **New** → **Blueprint** → connect the repository.
2. Render reads `render.yaml` and asks for two values:
   - `MONGODB_URI`: your Atlas string, with `fixtrail` as the database name.
   - `CLIENT_ORIGIN`: leave blank for now, then fill it in after step 4 below.
3. `JWT_SECRET` is generated by Render automatically.
4. Apply. Once the service exists, copy its URL, set `CLIENT_ORIGIN` to that URL under **Environment**, and redeploy.

### Option B: manual web service

1. New → **Web Service** → connect the repository, runtime **Node**.
2. **Build command:** `npm install --include=dev && npm run build`
   The `--include=dev` matters. In production, npm skips dev dependencies by default, and the build tools are dev dependencies.
3. **Start command:** `npm start`
4. Health check path: `/api/health`
5. Environment variables: the same list as Option A, with `NODE_ENV=production`, `NODE_VERSION=22`, `MONGODB_URI`, `JWT_SECRET` (32+ random characters), `CLIENT_ORIGIN`, `DEMO_LOGIN=true`, `DEMO_LOGIN_ACKNOWLEDGED=true`.

`DEMO_LOGIN` lets people sign in with just a name and an email. The server refuses to start in production unless `DEMO_LOGIN_ACKNOWLEDGED` is also `true`, so this is always a deliberate choice. Do not put real resident data in a deployment that uses it.

## 4. Check it works

1. Open the Render URL. You should see the login screen with the test-build notice.
2. Log in as a resident, raise a ticket.
3. Open a private window, log in as a service worker, take the ticket and work it.
4. Log back in as the resident: the tracker and status should match.

## Notes

- **Free hosts sleep when idle.** The first visit after a quiet period can take
  30–60 seconds. This is fine for a test build.
- **Data survives restarts** because it lives in Atlas, not on the server.
- **Real data** needs passwords, approval of resident accounts and a stricter
  database network rule first. See the PRD and TRD.
